# 播放诊断与导出恢复

按需阅读：语音重复/播放漂移、长片导出中断、缓存帧复用、成片旁白比对。先复现具体症状，优先修复共享根因；已有音频和画面能复用时保留。

## 语音重复：先区分发生在哪一层

| 观察 | 下一步 |
| --- | --- |
| 网页重复，原音频与 MP4 正常 | 检查播放器时钟、音频 currentTime 倒退、重挂载及多个播放器同时发声 |
| 单段原音频就重复 | 对照该段文案、TTS 输出与词边界，局部修复配音 |
| MP4 重复，单段原音频正常 | 检查 Sequence/剪辑时间槽、同一音源的重复挂载与混音时间轴 |
| 目前只知道“听到重复” | 从用户正在看的版本连续复现；能独立检查的先查，不先重生成全部 TTS |

连续播放时采集墙钟、`frame/fps`、活动音频 `currentTime` 与活动实例数。记录暂停、拖动、循环、章节切换等合法时钟跳变，排除后再判断异常。跨句子测试能发现只测 seek 或截图遗漏的问题；漂移容差结合设备负载与采样间隔确定。

### 已验证的一种 Remotion 根因

在 Remotion 4.0.523 的一次实践中，`frameupdate → setFrame → 父组件重渲染 → 新建内联 inputProps` 使播放相关 effect 反复重启，视频时钟落后；音频同步随后反复向后 seek，听起来像重复短句。没有观察到多个音轨重叠。这是版本与实现相关的案例，不是所有重复语音的解释。

确认该调用链后，保留真正的业务参数依赖，使 inputProps 身份稳定，例如：

```tsx
const inputProps = useMemo(() => ({mode, scenario}), [mode, scenario]);
return <Player inputProps={inputProps} /* existing props */ />;
```

不要把仅用于显示进度的 frame 放入依赖，也不要漏掉确实改变课程的参数。若共享播放器承载多个课程，对报错课程和另一使用场景连续回归，确认无非预期 seek、重叠或持续时钟落后。查阅已安装版本源码与 [Player best practices](https://www.remotion.dev/docs/player/best-practices)。

## 长片导出中断：判断是否值得续作

正常情况继续使用现有渲染命令；长片已生成大量帧、重做成本明显时才复用缓存。

1. **保存错误与现有产物**：日志、帧缓存、源版本与未提交差异、音频/素材版本、Composition、props、fps、尺寸、字体与渲染参数。源文件改变后，重新判断哪些帧仍然有效。
2. **按证据修复失败原因**：资源 404 时读取实际响应与服务目录，而不只检查源音频存在。曾遇到 `localhost:3000` 返回其他 WSL 项目的目录；改用确认可用的独立渲染端口后恢复。使用本机可用端口，不把案例端口固定推广到所有项目，也不终止无关服务。
3. **资源预检**：核对本次 bundle/服务下所有将用到的音频和素材路径，覆盖最后一章，避免运行到末尾才发现缺失。低内存时降低 concurrency，错开渲染、浏览器测试与额外浏览器；吞吐量下降时不要盲目提高并发。
4. **界定有效帧范围**：检查连续编号、文件完整性与边界可解码。复制缓存时可能取到正在写的末帧，重渲染可疑边界。补帧保持全局帧号；核对当前 API 对 frameRange 的编号方式，防止从零命名覆盖旧帧。
5. **补齐后再合成**：保持相同代码、props、字体、尺寸、fps、JPEG 质量等；源有变化则重做受影响区间及其时间依赖。仅当画面不依赖音频分析时，才可静音补渲染画面，再按原时间轴合成源音频。不是用一张静帧填补缺口。
6. **完整验收**：连续帧无遗漏/重复，音频不重叠或截断，整片可解码；抽查拼接边界、失败位置与片尾，核对旁白。记录成片哈希与实际恢复方式。只有缓存参数/来源无法确认或补帧仍不可靠时才放弃该缓存重做；磁盘空间不足则先报告并调整方案，保留唯一旧成片。

一次恢复的可行路径是：Remotion `renderFrames` 补指定帧区间 → 校验全部图片 → 按 `round(start * fps)` 放置各原音频 → FFmpeg 编码完整 MP4。仅在轨道没有变速、音量包络、交叉淡化或其他效果时，简单 PCM 放置才与原时间轴等价；存在效果就复用原混音实现。

区分渲染日志、命令退出状态和最终媒体证据。PowerShell 对原生命令 stderr 的包装、npm 配置警告可能混入日志；查看具体错误，不仅凭包装层状态宣称失败，也不忽略真正的渲染异常。记录失败阶段以便从该阶段恢复，避免为编码或检查器失败重做全部画面。

## 成片旁白与源音频比对

适用于报告重复、修复混音，或使用缓存帧重新合成音轨后；普通视觉小改不必引入新音频流水线。

- 先检查原始片段与时间槽，再将最终 MP4 和原始片段解码为相同采样率、声道的 PCM。复用已安装 FFmpeg；可以用 Python 标准库完成对齐和相关性计算。
- 在预期起点附近搜索小范围偏移，然后比对整段有声区间。只比首秒不能排除后半段重复、丢失或漂移。静音区域单独检查；归一化相关性不验证音量与削波。
- 采样率转换和有损编码可能引入小偏移或分数采样偏移；用已知正常的输出校准检查器，必要时细化偏移搜索。不要把粗搜索遗漏相关峰当作视频损坏，也不要为让失败通过而临时放宽标准。
- 本次未变速、无背景音乐的 8 段旁白合成，8 kHz 单声道比对、剔除两端各 0.1 秒后，相关系数最低约 0.999955，偏移为零。这是案例结果，不是统一验收阈值；有配乐、变速、降噪等处理时，分离旁白轨或换合适的检查方法。
- 输出结论写“源片段与导出音轨匹配”“连续播放采样无倒退”等实际证据。源音频本身的重复内容、发音质量、教学节奏与人类可理解性仍需审听；自动相关性不证明这些方面通过。
