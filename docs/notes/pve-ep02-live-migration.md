# PVE 02：VM 还在写内存，如何完成切换？

2026-09-13。约 7 分钟讲稿与分镜草案；先制作其中 30 秒机制样片。完整课件尚未制作。承接第一集 HA / fencing 的概念对照，**本集重新设定一个健康集群中的 C → B 迁移**，不是上一集故障现场的连续时间线。

## 场景与教学契约

三节点均有 quorum，源端与目标端健康，CPU / machine / 软件兼容，访问同一共享 NFS，具备适当的业务网络连通性。VM 100 无本例不可迁移的直通设备；采用 pre-copy，不包含本地磁盘搬迁、post-copy、源宿主机故障。NFS 是便于隔离变量的例子，不是所有热迁移的必要条件。

观众应能解释：为什么已传的内存还要重传；为什么需要最终暂停；为什么接收进程存在不等于目标正在运行；为什么 QEMU 传输完成后 PVE 仍有管理步骤。

保持源节点左、目标右、共享磁盘下方。蓝色表示迁移数据与明确标注的磁盘 I/O，绿色表示执行或管理指令，琥珀色表示脏页与暂停。每个状态变化有可见触发；数据抵达后目标页才更新。八个方块表示页组，v1 / v2 / v3 是教学标签，均不是线上协议格式。暂停窗口放大，不承诺实际停顿时长。

## 7 分钟旁白与分镜

时间为剪辑预算，正式配音后以实际词边界调整；不能将本表当作已完成的音频时间轴。括号中的观察动作不配音。

### 00:00–00:30｜这次保留运行状态（S1、S2）

**旁白：** 上一集，我们等旧节点被安全隔离后，在另一个节点重新启动虚拟机。它没有带走旧机器的运行内存。这次换一个条件：两个宿主机都健康，我们主动把正在运行的 VM 从 C 搬到 B。程序已经算到一半，内存里还有数据。热迁移要接住这些运行状态，而不只是让另一台机器从磁盘重新开机。问题是：源端还在修改内存，目标怎么追得上？

**画面：** HA 的“重新启动”小卡淡出；健康拓扑固定。C 内部展开 vCPU、RAM、虚拟设备；B 留空。固定 NFS 不随镜头移动。（留 3 秒观察。）

### 00:30–01:05｜分清三条路径（S1、S3）

**旁白：** 先把角色分开。PVE 管理迁移任务，准备目标并向 QEMU 发出控制命令。源 QEMU 和目标 QEMU 之间，才是运行状态的数据流。下方的共享存储，仍然保存同一块虚拟磁盘。Corosync 并不负责运输这批内存。画面把管理、迁移和磁盘访问分开，表示它们承担不同职责，不要求它们一定使用三张物理网卡。判断迁移卡在哪里，首先要辨认是哪条路径出了问题。

**画面：** 按旁白逐条点亮 QMP 控制、QEMU 迁移流、NFS I/O；不是同时放出所有粒子。共享存储名称保持不变。

### 01:05–01:40｜先准备一个不能执行的目标（S2、S3）

**旁白：** PVE 先检查运行状态、配置锁、资源和目标兼容性，再建立迁移所需的状态。目标宿主机启动 incoming QEMU，准备接收源端的数据。这时，目标上已经能看到一个进程，却不表示来宾指令已经开始执行。我们把目标 vCPU 的执行门保持关闭。源端继续运行，目标暂时只接收和装载状态。这种区别非常重要：如果把进程出现直接画成虚拟机开始服务，就把接收阶段和真正的交接混在了一起。

**画面：** 预检清单只展开本例条件；PVE → 配置锁 → 目标 incoming。B 的进程框出现，vCPU 门保持琥珀色。（提问停留 2 秒。）

### 01:40–02:15｜第一次传完，还不是最新状态（S1、S4）

**旁白：** 第一次预拷贝从源端读取内存，经过迁移通道，写到目标内存。看 P2：蓝色数据抵达后，目标显示版本一。但源端的程序还在执行，又把这组页改成版本二。目标那份数据没有凭空跟着变。脏页跟踪要记住：这些内容需要再同步。这里的脏，意思是自相关跟踪点以来发生了写入，不是内存损坏。版本号只是帮助我们看见差异，真实协议不靠画面中的这几个标签工作。

**画面：** P0–P7 依次抵达；来自 vCPU 的写操作落到 P2，源页更新，目标保留旧值，待传集合点亮 P2。放大同一页，不切换节点位置。

### 02:15–02:55｜重传与收敛（S3、S4）

**旁白：** 下一轮把变脏的部分再传过去。目标追上了，源端却可能再次写入，形成下一轮差异。所以，迁移时间不只取决于内存容量和网速，还取决于程序制造新脏页的速度。如果新增得太快，剩余状态就很难缩小。QEMU 和 PVE 有相关的收敛手段；我们检查的路径启用了 auto-converge，管理代码也可能调整允许的停顿。它们都有代价，不能把热迁移理解成任何负载下都无感。最终切换也不是等运行中的所有页永远不再变化。

**画面：** P2 v2 抵达 → C 再写成 v3；两条无单位示意条比较“新增待传量”和“传出量”。明确为定性模型，不伪装成测量曲线。

### 02:55–03:35｜最后为什么要暂停（S4、S5）

**旁白：** 当剩余状态和切换条件合适时，进入最后的交接窗口。先暂停源端来宾执行，阻止它继续沿着原来的执行流前进，再完成剩余内存以及处理器、虚拟设备等状态的同步。目标需要接续的是一致的运行状态，而不只是几个内存方块变成绿色。为了看清动作，我们把停顿明显拉长。真正的耗时取决于剩余状态、网络、设备和实现条件，不能从动画秒数推算。图上分开呈现内存与设备，不是在规定 QEMU 内部固定的序列化顺序。

**画面：** 源 vCPU 写脉冲停止，P2 v3 抵达；最终状态包从发送端进入 B。两边执行指示暂时都关闭，停顿区域持续可见。

### 03:35–04:10｜传输完成，还差管理交接（S3、S6）

**旁白：** QEMU 报告传输完成，说明这一层的工作到了完成状态，但不等于 PVE 整个迁移任务已经结束。在本例检查的代码路径里，PVE 还要移动 VM 配置的节点归属，再恢复目标端执行。注意下方的配置卡从 C 变为 B，随后 resume 进入目标。这是管理状态的交接，不是再把 RAM 复制一次，也不是把共享磁盘搬到 B。把这些步骤画成不同事件，才能解释为什么“内存传完了”和“目标继续运行了”之间还有区别。

**画面：** 三个独立状态灯：QEMU completed → 配置归属 B → resume。绿色控制脉冲落入目标 vCPU，随后执行门打开。

### 04:10–04:45｜源进程为什么还可能存在（S6）

**旁白：** 目标恢复后，程序从迁移来的状态继续执行。源端的旧 QEMU 进程随后被清理。所以某个很短的时刻，两台宿主机都有进程，并不意味着两个来宾同时执行。看指示灯：源端在交接窗口开始时就已经停下，目标到现在才恢复。下方依然是同一份 NFS 磁盘，只是本例中的来宾磁盘访问改由目标端发起。这里展示的是执行权的接续，不是一次来宾操作系统重启。

**画面：** B 指令与 I/O 恢复；C 进程框延后淡出。停留对照“进程存在”和“vCPU 执行”两个独立灯。

### 04:45–05:25｜运行状态连续，不代表所有连接都保证连续（S1、S2）

**旁白：** 现在把镜头拉到业务侧。CPU 和内存交接成功，是应用连续性的基础，但网络路径也必须接得上。相同的来宾地址，并不自动保证宿主机上的防火墙或连接跟踪状态全部可用。PVE 文档把连接跟踪迁移描述为尽力而为，还存在配置和版本条件。存储访问、CPU 能力、机器类型和软件兼容也不能略过。所以验收时，要分别观察迁移任务、来宾运行和真实业务请求。迁移任务成功，是一项证据；连接和应用是否达到要求，要有各自的证据。

**画面：** 保留小拓扑，放大外部客户端 → 目标业务网 → 来宾。分列任务结果、来宾运行、业务探测；不用一个绿色勾替代全部验收。

### 05:25–06:05｜切换之前失败怎么办（S7）

**旁白：** 再看一个有边界的失败场景：还在预拷贝，源端没有暂停，迁移传输失败，但源宿主机和控制路径都正常。此时目标从未开始执行，源端仍可继续。管理流程取消迁移并清理接收端等资源。不要把这个例子推广成所有迁移失败都能原地回滚：进入后续切换阶段，或者源端失联，处理条件就不同了。本集也没有启用 post-copy，不能把另一种迁移模式的故障行为直接套进来。

**画面：** 回到同一场景的预拷贝位置，只打断迁移通道。C 执行灯保持绿色；取消事件后 B 接收状态清空。画面明确“源端暂停前”。

### 06:05–06:35｜判断题（S3、S6）

**旁白：** 判断一下：目标已经收到了全部 RAM，是不是现在就可以让目标来宾执行？（留 6 秒。）不能只看 RAM。还要满足最终运行状态同步和相应管理交接等条件。在本例中，我们依次检查源端已经暂停、QEMU 完成最终传输、配置归属已经交接，以及目标恢复执行。任意把其中一个标志当作全部完成，都可能误读实际阶段。

**画面：** RAM 全绿而最终设备状态未就绪；目标门仍关闭。答案依次揭示必要条件，不新增虚构协议握手。

### 06:35–07:00｜带走一条因果链（S1、S6）

**旁白：** 记住这条链：运行中预拷贝，跟踪并重传变化；最后暂停并同步完整状态；完成管理交接，再在目标恢复执行。共享磁盘可以留在原位。与上一集的 HA 重启相比，这次保留的是运行状态。接下来还有一个问题：为什么配置归属能够在节点之间交接，多个节点又如何看到一致的配置？下一集，我们打开 pmxcfs 的内部。

**画面：** 沿用已看过的对象缩成因果链，最后只高亮配置卡，引到 pmxcfs；留 3 秒回看。

## 制作与专业审查意见

- 协议视角：区分 RAM 脏页跟踪与磁盘 dirty bitmap，不画 Corosync 承载内存；不宣称所有失败可回滚。
- 系统视角：PVE 管理状态、QEMU 传输状态、来宾执行与业务探测分开；检查的是本例调用路径，不泛化到所有模式。
- 教学视角：用同一页连续三次变化展示原因，先看现象再引入术语；长片加入一次判断题并留答题时间。
- 动效视角：数据抵达驱动接收侧状态，箭头落在组件边界；放大停顿但持续标记为教学编排。
- 取舍：复用现有 Remotion / SVG / Player 与 TTS，不增加视频平台、Agent 调度器或新的渲染框架。先评审 [30 秒样片](live-migration-30s.md)，再按上述分镜扩展。
