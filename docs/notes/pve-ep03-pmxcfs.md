# PVE 03：一次配置修改，如何成为集群共享状态？

2026-09-13。约 7 分钟讲稿与分镜；已从 30 秒样片扩展完整课件，制作与成片验收进度见 [完整讲解记录](pmxcfs-7min.md)。原样片见 [30 秒制作记录](pmxcfs-30s.md)。承接热迁移中的配置归属问题，但本集重新设定健康、已同步的三节点集群。

## 场景与教学契约

跟踪节点 A 对同一规范路径 `/etc/pve/nodes/B/qemu-server/100.conf` 的一次已进入 FUSE 的写操作。权限检查已通过，无并发写者、无 I/O 错误，各节点处于正常同步状态。描述字段及 W1、v1/v2 都是教学标签，不是协议中的实际消息格式。整次 GUI/API 保存可能包含临时文件、重命名和上层锁，本例不把单次文件操作冒充完整业务事务。

三节点各一票，预期票数 3、门槛 2，无 QDevice 或特殊仲裁设置。末段另做已经稳定的 A+B / C 分区对照，不模拟故障检测过程。已有配置可读不代表 VM 可恢复，也不代表允许继续修改配置。

观众应能解释：`/etc/pve` 的入口与状态在哪里；正常写操作怎样经组通信返回各节点；调用返回等待什么；为什么每节点都有数据库仍不等于能独立写入。

## 7 分钟旁白与分镜

以下是剪辑预算，完整配音后再做词边界对齐。所有速度和跨节点延迟均为教学编排，不是实测。

### 00:00–00:30｜三个入口，同一个配置对象（S1）

**旁白：** 上一集，热迁移最终改变了虚拟机的配置归属。现在先把迁移停在一边，追问一个更基础的问题：为什么在不同节点上，都能看到集群中的配置？看这个完整路径，它属于节点 B，但我们从 A 的文件系统入口访问它。路径相同，是比较同一个对象的前提。不同节点上的本地别名，不能直接当成同一个文件比较。

**画面：** 固定 A、B、C 三列，同一路径贯穿顶栏；先只点亮 A 的 FUSE 入口。配置页与虚拟磁盘图标分开，磁盘退出主画面。

### 00:30–01:05｜展开节点内部（S1、S2、S6）

**旁白：** 这个目录由 pmxcfs 提供。文件系统操作经过 FUSE 进入本机进程；进程里有内存配置树，还有访问本地 SQLite 数据库的代码。数据库文件保存本地配置状态。下方单独画出 Corosync，它承担节点之间的组通信。先记住这几个职责：文件入口、操作处理、内存状态、本地数据库，以及集群消息通道。

**画面：** 从 FUSE 向下逐层展开；pmxcfs 使用明确进程边界，Corosync 位于边界外。SQLite 是嵌入式后端，不画成独立数据库服务器。

### 01:05–01:45｜写入先经过资格检查（S2、S3）

**旁白：** 假设权限已允许，应用提交了一次写操作。FUSE 找到对应处理入口，集群模式下进入分布式配置处理路径。发送前还要确认本机有 quorum。允许写入，不等于已经修改完成；它只是允许这次操作进入后面的流程。消息携带路径、写入内容、偏移等信息，交给分布式状态机发送。这里跟踪一项文件操作，不把一次界面保存中的所有步骤压成一个消息。

**画面：** W1 从入口进入 quorum 门，门亮绿后才进入 DCDB/DFSM；内存仍保持 v1。角落显示 `cfs_plug_memdb_write → dcdb_send_fuse_message`。

### 01:45–02:25｜一致顺序包含发送节点（S4、S7）

**旁白：** 操作通过 Corosync 的 CPG 组通信发送。这里使用 AGREED 类型，关键是组内对交付顺序达成一致。发送节点自己也要接收这条操作，不能先随意改好本机，再把数据库文件发给别人。若有先后两条操作，各节点应按一致的次序处理。顺序一致，不表示三台机器在同一毫秒完成；动画故意错开到达时间，让我们看见这一区别。

**画面：** 放大 CPG 路径，显示 A 的本地回送以及 A→B、A→C。完整课程用 W1/W2 队列说明顺序，但不演示未经核实的并发冲突解决算法。不得把 AGREED 标注为所有节点落盘确认。

### 02:25–03:05｜各自执行，更新各自副本（S3、S5、S6）

**旁白：** 正常同步状态下，交付回调解析操作，再调用内存数据库的写入函数。各节点更新自己的配置树，并通过本地数据库后端记录这次变化。蓝色消息交付后，内存才变成新值，再显示本地数据库更新。处理过程中持有内部互斥锁，新的读取可能需要等待。不要把中间画面解释成应用已经读到了一个随意拼接的半成品。

**画面：** CPG→DCDB→memdb→SQLite，抵达后才变色；更新中的 FUSE 标为“读取等待”。不把三个数据库图标合并成远程共享盘。

### 03:05–03:45｜返回结果究竟等谁（S4、S5、S6）

**旁白：** 发送路径等待自己发出的消息在本机被交付、处理，并记录处理结果。结果再沿本机调用链返回。看 A：本地处理已经完成，所以调用可以返回；C 的后端处理在这个示意时刻仍可稍慢。这个等待条件，不是逐台收集磁盘回执。SQLite 事务提交也不能直接翻译成每次写入都已获得断电持久性保证，那还涉及实际日志和同步设置。

**画面：** A 的绿色返回线亮起，C 保留“更新中”。圈出本机结果槽，不添加 B/C→A 的虚构 ACK。停留 3 秒供观众比较。

### 03:45–04:20｜读取走本机（S2、S5）

**旁白：** 配置稳定后，读取通过本机文件入口访问本机内存状态。不是每读一个文件，都向其他节点重新查询一次。配置复制让各节点维护自己的副本，读取路径则使用这份本地状态。正在执行的本地修改可能让读取等待；网络分区之后还能读到已保存配置，也不等于它仍有资格产生新的集群修改。

**画面：** 用绿色读请求往返 FUSE 与 memdb，CPG 路径保持静止。复用同一对象，避免换路径导致观众误认跨节点读取。

### 04:20–05:00｜失去 quorum 后的新写入（S1、S3）

**旁白：** 现在切换到另一个已稳定的场景：A 和 B 仍组成多数，C 只有自己的一票。在 C 上尝试新写入，会被 quorum 检查拒绝，不能像健康场景那样把新操作继续送入集群写路径。已有配置仍然可以读取。这里讨论配置文件系统的限制；虚拟机是否继续运行、何时由 HA 恢复，要回到第一集的 watchdog 和安全接管条件。

**画面：** 明示“稍后的分区对照”；A-B 实线，通往 C 的路径虚线；C 的红色拒绝沿原路返回，v2 不再变化，随后绿色读取返回 v2。

### 05:00–05:40｜顺序不等于业务事务（S8）

**旁白：** 还有一层容易混淆：文件操作有一致顺序，不代表上层的一串读取、判断、修改就自动成为不可分割的事务。两个业务操作仍然可能需要协作锁来保护临界区。PVE 的集群库提供这样的封装，例如通过集群文件系统里的锁目录竞争锁，进入临界区前刷新配置，完成后释放锁。具体业务是否使用它，仍要查看自己的调用链，不能把这个例子套到所有虚拟机操作上。

**画面：** 在节点内部图上方增加两个调用者，只展开“争取锁→刷新→业务操作→释放”。不把锁目录、memdb 内部互斥锁和 VM 配置锁画成同一个锁。

### 05:40–06:20｜用边界判断问题（S1–S8）

**旁白：** 如果写入卡住，应区分入口、quorum、消息交付、本机处理和上层锁。如果文件还能读取，不能据此断言集群写入正常；如果调用已经返回，也不能据此断言所有节点都完成了独立磁盘同步。新节点加入、状态重新同步、数据库错误和并发冲突需要单独的异常流程，本集这条健康路径并没有覆盖它们。诊断时先把观察结果放回正确的层次。

**画面：** 逐项高亮五个检查位置，每次只出现一个问题。异常恢复作为边界卡片，不用猜测的箭头补齐。

### 06:20–07:00｜判断题与回看

**旁白：** 最后判断：C 上还有配置数据库，它就能在失去 quorum 后独立写入吗？不能。再判断：A 的写调用返回，是否意味着收齐了三台机器的落盘回执？也不能这样推断。请沿着这条路径复述：文件操作进入本机，经过仲裁检查，由组通信按一致顺序交付，各节点更新本地状态，调用者取得本机处理结果。入口、顺序、返回条件和持久性，是四个需要分别理解的问题。

**画面：** 两题各留 3 秒再揭示答案；最后重放同一条因果链，不再新增组件。

## 本轮专业审查与修订

- 分布式系统：把“同步写”等待条件展开为本机交付结果，删去全节点 ACK 的暗示；节点完成时刻错开。
- 操作系统：Corosync 与 pmxcfs 分进程绘制；内存更新但后端未完成时显示读取等待。
- 存储：使用“本地数据库更新完成”，不把事务提交称为逐次断电持久化；虚拟磁盘明确排除。
- 教学：先讲健康路径，再用稳定分区作对照；保持对象路径、节点位置和组件位置不变。
- 动效：状态必须在触发事件之后变化；跨节点消息与本机返回用不同颜色，不用无意义的循环粒子。

以上为制作中的专业视角核查，并非外部专家背书。尚未进行真实 PVE 集群写入、抓包或断电实验。
