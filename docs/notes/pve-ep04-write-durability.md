## 固定场景与学习目标

从来宾块设备 WRITE 开始，追踪 VirtIO Block → QEMU raw/file 后端 → Linux 文件系统/宿主页缓存 → 设备易失写缓存 → 非易失存储，再观察完成结果返回。选用显式 `cache=writeback`、`aio=threads`、本地文件系统中的 raw 普通文件，虚拟写缓存开启。此处不是 PVE 默认值说明或缓存配置推荐。

假定文件系统与设备正确兑现同步/刷新语义，无 I/O 错误、无并发新写入。教学选择后台回写尚未完成的一个可能窗口，并非每次 WRITE 都只留在内存直到 FLUSH。W1、v1/v2 是请求/版本标签，不代表扇区写入原子性。设备采用具有易失写缓存的示例，不外推到所有 SSD、RAID、NFS、ZFS 或 Ceph。

学习后应能回答：完成由哪一层发出？对应数据此时在哪里？持久化还依赖什么条件？`cache=none` 为什么不能理解成整个系统不存在缓存？

## 七分钟分镜与旁白草案

固定四列位置，局部放大当前组件；每次只高亮一条因果链。蓝色表示写请求/数据，琥珀色表示刷新控制，绿色表示完成返回。下层收到请求才更新状态；介质持久化后，绿色结果逐跳返回，不同时点亮全链。

| 章节 / 时间 | 画面、内部动作与停顿 | 旁白草案 |
| --- | --- | --- |
| 01 · 0–30 秒：成功的含义 | Guest 的 WRITE OK → 展开页缓存 v2 / 介质 v1；停两秒 | 虚拟机收到一次写入成功。如果宿主此时突然断电，这份数据一定还在吗？先别急着回答。成功是一条由具体层发出的完成消息，它不一定意味着数据已经越过所有易失缓存。这集只追踪一个块设备写请求：数据往下走，完成往上走。我们要找清楚，两条路径分别承诺了什么。 |
| 02 · 30–65 秒：责任图 | Guest 队列、QEMU 设备模拟/块后端、Host 文件系统/页缓存、设备缓存/介质逐层展开 | 先定位参与者。来宾把请求交给虚拟块设备，QEMU 处理设备请求并交给存储后端。本例后端是一份本地 raw 文件，文件写入经过宿主 Linux。再往下，是存储设备自己的缓存和非易失存储。宿主页缓存与设备缓存是两个不同位置。PVE 负责配置和组织虚拟机；本次 I/O 的执行路径，需要继续深入 QEMU 和宿主存储栈。 |
| 03 · 65–100 秒：固定配置 | 显式配置标记；PVE 配置箭头一次性落到 QEMU 后退暗 | 为了让结论可核查，我们固定一个案例：虚拟写缓存开启，使用回写模式，本地 raw 文件，以及线程式文件 I/O。这是教学选定的路径，不代表 PVE 的默认配置。切换为直通块设备、网络存储或其他格式后，下层实现会变化。先理解这条具体路径，再把同样的问题带到别的后端：哪里可以缓存，哪里等待，谁确认持久化。 |
| 04 · 100–145 秒：WRITE 去程与回程 | W1 穿过 VirtIO/块后端，页缓存变 v2；WRITE 完成返回，介质仍 v1 | 现在提交 W1。QEMU 的虚拟设备接收写请求，块后端执行文件写入。回写模式下，数据进入宿主页缓存后，这次写可以完成。注意回程：完成结果经过 QEMU，最终通知来宾。此时来宾得到 WRITE OK，可我们刻意选择了后台回写尚未完成的时刻，设备还没有持久保存新内容。因此，“请求完成”与“抗断电保存”不能直接画上等号。实际后台也可能更早写出，动画展示的是允许出现的窗口。 |
| 05 · 145–180 秒：断电反例 | 冻结 WRITE OK 为历史证据；易失状态淡出；不演出必然恢复 v1 | 把时间停在这个窗口，只改变一个变量：模拟宿主和易失缓存失去供电。之前收到的 WRITE OK，是已经发生的历史结果，却不能把内存变成非易失存储。这里的正确结论是，新内容的留存没有保证。我们不把重启后的结果画成必然完整回到旧值，也不承诺写入原子性。这是语义推演，不是已经完成的真实断电实验。 |
| 06 · 180–230 秒：FLUSH 往下执行 | FLUSH 到文件同步；脏数据到设备缓存；设备兑现刷新到介质 | 回到正常供电的路径。来宾现在发出刷新请求。它不是第二份数据，而是要求下层兑现相关持久化条件。QEMU 的 VirtIO 刷新处理进入块后端，再进入文件后端；本例线程路径执行文件同步调用。接下来要分开看两件事：宿主把相关脏数据写下去，设备再兑现其缓存刷新语义。不能只向设备发一个刷新，却把本该写出的数据留在宿主页缓存。画面用两种颜色，分别追踪数据和控制。 |
| 07 · 230–265 秒：完成返回 | 介质 v2 → 设备 → fdatasync → 块后端 → VirtIO → Guest FLUSH OK | 当下层完成持久化，结果还要向上返回。先是宿主同步操作完成，再经过文件与块后端、虚拟设备，最后来宾收到 FLUSH 完成。别把这些状态同时点亮：下层已完成时，上层还可能在等待结果。缓存里的副本也不必消失，仍有副本并不等于仍是脏数据。这条保证依赖每一层正确兑现语义；遇到 I/O 失败，就不能继续照常播放成功回程。 |
| 08 · 265–305 秒：缓存模式 | 对比虚拟写缓存、绕过页缓存、忽略刷新；设备缓存图始终保留 | 判断缓存模式，不要只读名字。至少拆成三个问题：虚拟设备是否报告写缓存，宿主是否绕过页缓存，刷新是否被忽略。以 QEMU 文档里的组合来看，none 会绕过宿主页缓存，但不表示设备没有缓存，也不取消刷新语义。unsafe 则允许忽略刷新请求，不能沿用刚才的持久化推理。回写模式本身也不等于数据必然丢失，关键在于完成语义和整个栈是否正确配合。这里是在解释机制，不是给所有后端套同一个配置建议。 |
| 09 · 305–340 秒：FUA | 标注“Linux 块层语义”；PREFLUSH 覆盖先前完成写，FUA 约束本次写的完成 | 再补一个常见混淆：刷新和强制单次写入持久化，不是同一个问题。Linux 块层的预刷新语义关注此前已经完成的写；FUA 则要求本次写入到达非易失存储后，才能报告该请求完成。具体栈可能把这种要求转换为不同底层操作。本段只是比较语义，不表示本例 VirtIO 请求直接携带了同名 FUA 命令，也不把一个文件同步调用固定等同于一条物理命令。 |
| 10 · 340–380 秒：应用边界 | 上方添加应用/文件系统虚线框；应用同步、日志、错误处理标为另需核查 | 把视角再向上一层。我们从块设备请求开始，没有从应用的 write 调用开始，更没有证明整笔数据库事务已经安全提交。如果业务说“保存成功”，还要查清应用何时请求同步、如何处理失败，以及文件系统和数据库的具体协议。下层持久化是重要条件，却不是备份、副本和事务原子性的通用替代品。架构评审时，应把这些保证分别列出，再逐层建立证据。 |
| 11 · 380–420 秒：三问验收 | WRITE OK 时 v2 在哪里？介质 v2 后 Guest 是否立即知道？none 是否关闭设备缓存？ | 最后用三个问题检查理解。第一，收到 WRITE OK 时，新数据一定在哪里？本例能确定的是写已完成，不能仅凭它保证介质持久保存。第二，介质已经完成持久化，来宾是否立即知道？还需要结果沿栈返回。第三，none 是否关闭了所有缓存？没有，它不能代表整个设备链。以后看到任何“写成功”，都追问：谁报告的完成，数据到了哪里，还依赖哪些保证。 |

## 本轮专业修订与后续验收

- 存储：区分 WRITE/FLUSH 完成；先写出相关数据，再让设备兑现刷新，完成最后返回。
- 虚拟化：明确 PVE 配置、QEMU 执行、下层兑现的边界；显式固定参数，避免把上游默认值当成 PVE 默认值。
- 教学：断电只改变一个变量，保留历史 WRITE OK；不画成必然完整回滚 v1。缓存保留副本与脏状态分开解释。
- 动效：固定四列与内部组件，数据、控制、结果分色；接收后才更新状态，收到结果后才显示完成。
- 验证：900 帧检查因果顺序与倒退确定性；另做浏览器断电预设、控制与 MP4 完整解码。结果见样片记录。

完整制作保留先前样片，按实际旁白重新分配时间。缓存模式与 FUA 用局部对照图，避免整图同时承担所有后端。未进行真实 PVE I/O 或断电实验；以后实验需先固定 VM、镜像/文件系统、设备与固件条件，再单独安排授权，不能用动画代替硬件证据。
