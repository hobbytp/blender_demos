# HA / fencing：30 秒内部机制样片

2026-09-13。承接[首集脚本与依据](pve-ep01-ha-fencing.md)，用户批准继续后实现。此次只交付机制样片与正常对照，7 分钟全片尚未制作。

## 观看与复现

- 视频：`out/ha-fencing-30s.mp4`（本地导出，不纳入 Git）。
- 浏览器：运行 `npm run dev`，打开 `http://127.0.0.1:5173/?sample=ha`。
- 场景：默认持续分区；可切换正常对照（无旁白），切换时回到起点。章节按钮选择故障场景并暂停到对应片段。
- 生成配音：`npm run voice:ha`；渲染：`npm run render:ha`。Windows 使用 `npm.cmd`。
- 源码：`src/HaPilot.tsx`、`src/ha-timeline.ts`；配音沿用 `scripts/dark-narration.py` 和 Yunxi 声线，未增加生产依赖。

## 演示范围

以 C 的剖面和 B 的决策视角并排展示：持续分区、失去 quorum、续锁失败、客户端续期中止、watchdog-mux 停喂、主机复位，以及多数侧获取旧节点 agent lock 后的 fencing 判定与 recovery。

此片停在恢复入口，目标 VM 始终尚未启动；共享 NFS 磁盘固定在原位。没有把配置写入资格画成直接停止 VM，没有远程“已关机 ACK”，没有磁盘搬运或内存迁移。B 的完整 watchdog 保护及后续 CRM/LRM 管理状态往返留给全片，当前简化应结合首集前提理解。

动画帧由帧号直接推导；两侧是同一次故障的并行过程，播放时间不是协议计时。状态测试验证的是本片固定情境，不是任意部署下的 HA 协议证明。具体软件包组合与 watchdog 驱动尚未作实机验证，不使用“精确 60 秒恢复”之类表述。

## 专业审查与落实

- 协议：区分“导演看到 C 已复位”和“B 仍不能确认旧节点状态”；安全依据脉冲从 B 本地 pmxcfs 返回 CRM。
- 系统实现：本地 UNIX socket 续期与设备喂狗分两条线；失去 agent lock 后不继续画无条件成功续期。
- 状态表达：离线等待阶段保留 `started` 管理状态，另外说明等待离线判断；不把它等同于 QEMU 或应用状态。
- 存储：C 的旧实例停止后，其 I/O 粒子停止；B 的路径只表示存储可访问，没有新实例 I/O。
- 教学：正常对照显示正常链条，避免灰色故障步骤被误读为必然结果；两侧事件条保留全局因果参照。
- 后续建议：全片增加正常时锁更新的完整往返、B 的 watchdog 保护和 CRM/LRM 状态协作；先用样片检验观众能否解释“有 quorum 仍不能立即恢复”。这些深度内容不硬塞进 30 秒。
